# Roadmap

The end state is the one Blast Corps reached (`../BlastCorps`): every ROM
rebuilds byte for byte from one source tree, all of the game's code is C
(no `GLOBAL_ASM` left, and no handwritten asm in the port), the ROM's assets
are editable files that rebuild to the same bytes, and the same C builds a
PC port (native and WebAssembly). Bomberman 64 adds one goal on top: online
multiplayer over WebRTC, native and browser alike (docs/NETPLAY.md).

Versions: **us** (`NBME`) is the working version, and **eu** (`NBMP`) and
**jp** (`NBMJ`, *Baku Bomberman*) build from the same C with `#if`s, the
way Blast Corps does it (its CLAUDE.md, "Versions"). See docs/LAYOUT.md
for the ROMs and README.md for the hashes.

## Phase 0 — scaffolding (done)

- Repo, submodules (asm-differ, asm-processor, m2c, decomp-permuter), a
  venv with pinned splat64/spimdisasm, IDO 5.3 from decompals'
  static recompilation (`tools/get_ido.sh`).
- `bm64.<v>.sha1` for each ROM, and `make check`.
- The top-level layout of both ROMs (docs/LAYOUT.md, `tools/layout.py`) and
  the Hudson LZSS codec (docs/COMPRESSION.md, `tools/hudson_lzss.py`).
- A ROM-free CI job (`.github/workflows/ci.yml`).

## Phase 1 — stage 1: the ROM as named pieces, matching (done)

`make extract && make` builds each ROM from its pieces, sha1-checked.

- `bm64.<v>.yaml` (26 segments, generated by `tools/layout.py`) has splat
  cut the fixed part: header, IPL3, boot_code, zerojump, the two ROM
  tables, main_code and the pads between them.
- Each of the 15 archives is one segment. `tools/assets.py extract`
  replaces it with `assets/bankNN/`: every entry inflated (`NN.bin`) or
  stored (`NN.raw`), each overlay bank's index as `index.yaml`, and an
  `archive.yaml` with the order, the slot size and the tail bytes.
  Extraction fails unless the files rebuild to the ROM's bytes.
- `make` links the ROM with the archives rebuilt from those files
  (`assets.py build`, with Hudson's encoder, which matches all 961
  compressed entries in each ROM). An edited entry can change size, as
  long as its bank still fits its slot.
- `tools/test_lzss.py` and CI check the codec without a ROM.

**Not yet:** a bank can't move or outgrow its slot. main_code finds the
overlay banks by number (`ROM >> 17`, the table at `0x30800`) and the
asset archive by address (`lui a0,0x30`). Placing banks by size, as Blast
Corps' `rom_syms.py` does, needs those references to become symbols. That
comes with stage 2's disassembly, and the `SHIFT` build will prove it.
Editable formats for what the entries contain (models, textures, sound)
are phase 5.

## Phase 2 — stage 2: code split and reassembly (done)

`make extract && make` disassembles every code segment and builds the ROM
back from the asm, sha1-checked, for us, eu and jp. docs/LAYOUT.md, "Stage 2",
describes the pieces:

- **One code image** (`assets/code.bin`): the ROM below 0x120000 as it is,
  then all 95 overlays inflated. One splat config (`bm64.<v>.yaml`, from
  `tools/layout.py`) splits it, one link rebuilds it, and `tools/rom.py`
  packs the ROM from it and the archives, recompressing the overlays.
- **Modules:** boot_code, zerojump (fixed page, handwritten), main_code
  and every overlay (`ovl_BB_EE`, VRAM 0x80043000, one shared RAM id,
  names `func_ovlBB_EE_XXXXXXXX`). Each module's ZeroJump stub block is a
  `hasm` object (`<module>_zerojmp`). Each module's entry function is its
  own object, and main_code's persistent tail (loaded once by the boot
  thread) is too.
- **Objects:** text is split where IDO's 16-byte padding shows an object
  boundary and no branch crosses it (334 objects in us). Every boundary
  found is also in the reference decomp's split; some real ones are
  missing (a function that ends on a 16-byte boundary leaves no padding).
  Phase 3 fills those in as libultra's objects are identified.
- **Nothing absolute:** `tools/postsplit.py` makes every reference into a
  module relative to a label (mid-object references, data words however
  splat typed them, module ends, zerojump's ROM range). `tools/find_abs.py`
  finds 0 addresses left without a relocation in either version.
- **SHIFT=1** pads every movable module after its entry and before its
  data (`tools/ld_fix.py`). The fixed ROM positions stay put, and the
  segment size table is written from the link. `make shift-check` runs the
  shifted and the original ROM headless in mupen64plus, from a blank
  EEPROM, with a scripted controller (mode select, a new file, the
  opening, the world select, then walking and bombing in the first stage).
  Both versions give identical data (boot_code, main_code, the loaded
  overlay) at nine checkpoints up to frame 24000. The game seeds its RNG
  with `osGetTime()` when main_code starts, and the shifted build's bigger
  DMAs (main_code is one 2 KiB unit longer, every overlay 0x20 bytes)
  change the cycle count there: unpinned, the seed differs, a stage's
  random placement takes another number of tries, and the frame counters
  drift (11 frames by 1800 in eu). So both ROMs run with that one seed
  pinned. bss isn't compared: thread interleaving within a frame, clock
  values and stale overlay bss differ for the same timing reason. A build
  with a process's entry pointer left absolute fails every checkpoint.

**Per-object `.data`/`.rodata`/`.bss`** come from the compiler: a
first heuristic for the .data/.rodata boundary (above every stored-to
address, below every jump table and float constant) disagreed with the
reference decomp in 26 of 95 overlays (floats in `.data` are loaded with
`lwc1` too, and tables of function pointers look like jump tables), and
the reference's own boundaries are partly guesses. Instead,
`data_split.txt` lists each module's C objects from its first on with the
section sizes IDO builds them to, and `tools/layout.py` cuts the module's
block object by object: `.data`/`.rodata`/`.bss` subsegments for those,
asm `data`, `rodata` and `bss` for the rest (docs/DECOMPILING.md, "Data",
has the workflow and `tools/data_split.py`, `data_c.py`,
`inline_rodata.py`). Without a cut a module's data is one `rodata` block
(as rodata so that spimdisasm labels its jump tables) and one bss block.
Cut so far: all of ovl_09_01 (its boundary is the compiler's,
0x80044990) and main_code's first three objects after its RSP code. The
SHIFT=1 image with the cut is byte-identical to the one from the asm
alone. The rest grows object by object with phase 4.

## Phase 3 — libraries (done)

docs/LIBULTRA.md has the details.

- **libultra is 2.0I** as decompals/ultralib builds it (`libultra_rom`,
  IDO 5.3, its own flags: libc, gu and libaudio `-O3`), in both versions.
  ultralib's D to I builds are the same code, and J/K/L don't match.
  `tools/build_ultralib.sh` builds every revision, and `tools/libmatch.py
  --scan` compares them.
- `tools/libmatch.py` and `tools/gen_symbols.py` (Blast Corps') name 370
  functions and 54 globals in boot_code and 12 functions and 1 global in
  main_code, in us, eu and jp alike (`symbol_addrs.<module>.<v>.txt`). EU's
  libultra (and jp's) is byte for byte US's. Only a 0x60-byte gap moves.
- Library objects whose boundaries the padding didn't show are split
  (`lib_objects.<v>.txt`, read by `tools/layout.py`): 397 text objects in
  us instead of 334.
- **libaudio** is 2.0I's libaudio, not an older audio library. All of it
  matches but `alSynStartVoiceParams`, which is Hudson's patch (voices
  centred when the game's mono flag is set), now C.
- **What no ultralib build matches** is an older SI/PI/controller pak
  layer: `osPfsReSizeFile` (which the SDK removed in 2.0I), 4K-only
  EEPROM, the Rumble Pak without `__osMotorinitialized`, PIF RAM cleared
  word by word, waits through `osClockRate`, and more; `__osException`
  with 2.0I's code but an older SP acknowledge; and 2.0I's own static
  functions (`sndplayer.c`, `_Putfld`, `_Genld`) that had no name. All of
  it is C (or `exceptasm.s`) in `src/libultra`, ultralib's 2.0I files with
  the differences, matching in us, eu and jp (docs/LIBULTRA.md, "What 2.0I
  doesn't reproduce"). `make libultra-ref` builds them as a reference
  library, so gen_symbols.py names them and their variables.
- **Not yet:** `osUnmapTLBAll` (older too, but EU's 0x60-byte gap follows
  it) stays asm, and the rest of the matched libultra isn't C (it needs
  no decompiling: ultralib's 2.0I files compile to it). Overlay copies of
  `osSpTaskYield`/`__osSpSetStatus` aren't named yet (one image, shared
  VRAM).
- **Hudson's allocator** is GNU malloc's `gmalloc.c` (1995), IDO 5.3
  `-g -mips1 -DPAGESIZE=0x1000`, a byte-exact match for ROM
  `0xB3B70-0xB5E50` in us and eu (`0xB3250` in jp), named in
  `symbol_addrs.libmalloc.<v>.txt`. docs/LIBMALLOC.md has the details, the
  checking tool and the licence (LGPLv2+).
- Only library code gets real names until the game's code is understood.
  Don't guess names.

## Phase 4 — decompilation (us, then eu)

The pipeline is in place (docs/DECOMPILING.md has the loop and the
evidence for the flags):

- A text object is C when `src/` has its file; `tools/layout.py` makes it
  a `c` subsegment, `tools/c_stub.py` starts the file with every function
  GLOBAL_ASM, and asm-processor builds it with IDO 5.3. `include/` has the
  ultra64 types and `common.h`.
- Flags: Hudson's game code is `-mips1` (load delay slots filled, no
  branch-likely) at `-O2` by default; `-O3` files are listed in the
  Makefile (IDO's `-O3` emits a file's functions in reverse order, which
  is the quickest test), and main_code's entry is `-g`. Libraries
  (boot_code, main_code from its ZeroJump block on) are `-mips2`.
- Tools: `tools/m2c.sh`, `tools/fdiff.py` (and asm-differ's
  `diff_settings.py`), `tools/permute.sh`, `tools/progress.py` (per module,
  overlays per bank or each).
- Done so far, matching in us, eu and jp: `main_code_entry` (func_80225800,
  `-g`), `40040` (func_80225840, main_code's main function, with its
  `.data`), `40300` (all seven functions: a bump allocator and Hudson's
  string/memory helpers, and its `.data`), `80420` (four of five;
  func_80265D10 is a run of 13 empty functions spimdisasm sees as one),
  and all of ovl_09_01: its entry and `120010` (seven functions and the
  twelve empty ones, with its `.data`, `.rodata` jump table and `.bss`).
  Then, data-free functions only: `404C0` (the ROM file system: 15 of
  18), `40FB0` (the overlay loader, all six, `-O3`), `5E090` (7 of 7),
  `87190` (the resource cache, 8 of 8), `87730` (9 of 10), `99F40`
  (the tile maps, 12 of 14), `A4860` (game flags, 12 of 13) and `B11F0`
  (19 of 25).
  docs/DECOMPILING.md has how `-O3` objects are told apart and what
  Hudson's C looks like.
- libultra's unmatched objects (phase 3): 28 objects in `src/libultra`,
  `-mips2` with 2.0I's flags, seven of them owning their data through
  `data_split.txt`'s placements, and `os/exceptasm.s` assembled by IDO.
- eu from the same C: `tools/vermap.py` (docs/LAYOUT.md, "The US to EU
  map") aligns eu's functions to us's by masked bodies and maps the data
  through them (`vermap.eu.txt`). `make extract` for eu renames splat's
  names to us's through it, so eu's asm and the C use us's names
  everywhere, and eu-only things get a `_eu` suffix (there are none yet:
  99.9% of the functions are identical, the other 8 changed).
- jp from the same C, matching from the start (the stage 2 build, the
  shift check, libultra's C and every decompiled object): `vermap.jp.txt`
  pairs 98.5% of the functions as identical (59 changed, 46 us-only, 33
  jp-only, in boot_code, main_code and 10 overlays; docs/LAYOUT.md, "The
  US to JP map"). jp's objects carry us's names, so the C files are the
  same objects, and `tools/split.py` gets splat to write their GLOBAL_ASM
  functions. Its assets (text pictures, voices, 870 entries) extract and
  rebuild like us's (docs/ASSETS.md, "US and JP").

**Not yet:**
- Per-object data beyond the cut (phase 2): an object outside the run
  `data_split.txt` lists from its module's first must still produce no
  `.data`/`.rodata`/`.bss`, unless data_split.txt places its sections on
  their own (so far only library objects, whose addresses
  `tools/data_split.py --place` finds). Each module's cut grows from its start as
  objects are decompiled with their data (docs/DECOMPILING.md, "Data");
  main_code's .data/.rodata boundary isn't shown yet.
- `#if VERSION_EU`/`#if VERSION_JP` in the C for the changed functions
  and the versions' data, and `version_ifs.py` (Blast Corps) for
  version-specific GLOBAL_ASM lines, when the first of those is
  decompiled (docs/DECOMPILING.md, "Versions").
- Hudson's game code is likely all C. Only libultra's `.s` files are real
  asm (`src/libultra/os/exceptasm.s` so far), and the port doesn't use
  those.

## Phase 5 — assets

Inventory the asset banks (models, textures, palettes, animations, the
sound banks and sequences), extract them to editable formats, and rebuild
them matching. The ROM link then places everything by built size, so an
edited asset can change size. Blast Corps' `tools/assets.py` and
`assetlib/` are the template. For the port, the remakeable assets
stay out of the executable and are loaded from the user's ROM at startup
(`ASSET_INIT`, as in Blast Corps).

The inventory is done: `tools/inventory.py` classifies every archive entry
(`docs/inventory.<v>.csv`), and docs/ASSETS.md has what is in them, how the
code finds them and what is still open. Only bank 0x18 holds assets (873
entries: 639 models, 129 images, 96 stage maps, two sound containers); the
other banks are overlay code.

Done so far: the 129 picture entries of bank 0x18 are PNGs
(`tools/assetlib/bm64image.py`; indexed CI4/CI8 with their palettes, RGBA32,
pads kept as data), rebuilt byte for byte and recompressed, edits work
(`tools/test_assets.py`); docs/ASSETS.md, "Pictures as PNGs". The 652
models (641, and the 11 picture files with a model behind them) are a yaml
each, with their textures as PNGs (`tools/assetlib/bm64model.py`): the
record chain, display lists as F3DEX 1.21 text with addresses as block
references, vertex tables, the node hierarchy, the poses and animation
tracks; a block can change size and everything after it moves.  All
rebuild byte for byte in us, eu and jp, edits work; docs/ASSETS.md, "Models as
yaml". Next: stage maps, the stored tables, sound, and the meaning of the
animation tracks' fields.

## Phase 6 — PC port

The same architecture as Blast Corps' port (its docs/PORT.md):

- One CMake build. The game's C, compiled by the host's compiler, in host
  byte order and pointer size. `#ifdef TARGET_PC` in `src/` for port-only
  changes. Native pointers, with `Gfx` as wide as a pointer.
- libultra replaced by a host layer (threads by ucontext or host
  threads, one at a time; VI, PI/DMA, SI/controllers, the EEPROM or
  controller pak as files). The RSP/RDP is a display-list renderer, and
  audio runs through libaudio's C.
- **Overlays:** on the N64 they share VRAM. In the port every overlay is
  linked in at once, with distinct symbols, and "loading" an overlay
  selects its code and resets its data/bss to the ROM's initial values.
  The zerojump table becomes a table of function pointers.
- Reuse is preferred over rewrite. Blast Corps' `port/host`, renderer and
  `libaudio` port are the starting point. Whatever is game-agnostic is
  shared or copied with attribution in NOTICES.md.
- Tests from the beginning: deterministic headless runs against committed
  references (`port/tools/test.py` in Blast Corps), sanitizers, a
  big-endian host and a 32-bit host. The determinism work is also netplay's
  foundation (docs/NETPLAY.md, "Requirements").

## Phase 7 — WebAssembly

emsdk, headless under node for the tests, and a page (`port/web/`) that
asks the player for their own ROM. GitHub Pages builds it from the
repository alone, as Blast Corps' `pages.yml` does.

## Phase 8 — online multiplayer

docs/NETPLAY.md. Its port requirements (determinism, a stepping API,
snapshots and cross-host hashes) start in phase 6. The network code comes
after the port runs battle mode correctly.

## Out of scope, for now

- The **Japan** ROM in this directory (`NHAJ`) is a different game:
  *Bomberman 64* (2001), released only in Japan, and not the Japanese
  release of this one. It is hashed in README.md for completeness. It
  would be its own project. (*Baku Bomberman*, `NBMJ`, the Japanese
  release of this game, is the `jp` version.)
