## Loaders

- **0x30000 is the segment size table**, not a "ROM header table". The ROM
  is cut into 128 KiB segments (number = ROM >> 17), and byte n is segment
  n's size in 2 KiB units, where 0 means 0x80000. Boot's
  `0x800007F0(seg, dst)` DMAs `seg << 17` for that size. The rule is
  ceil(size / 2 KiB), with exceptions: bank 0x16 is 0x40 although its
  contents fit in 0x07, and the asset archive (0x18) is 0. The bytes
  from 0x19 on are filler (0x20 is 0x6F in us and 0x70 in eu, the rest
  0x40). Keep the recorded values, and raise one only when a bank grows.
- **The boot thread (0x80001750)** loops forever: load segment `*0x80024818`
  (initially 2, main_code) to 0x80225800 and call it. Before the loop it
  DMAs ROM `0x40000 + tbl[2] * 2K`, size `tbl[3] * 2K` (0xBF800–0xC0000), to
  0x802A5000. That page is loaded once and is not reloaded with
  main_code, so main_code's data from 0xBF800 on persists across reloads.
  main_code's bss (0x802A5300) lies inside that page's zero tail.
- **0x30800 is the file table**: two bytes per file id, the segment and
  then a 2 KiB offset. main_code DMAs it to 0x8019B0D0. The overlay loader
  `0x8022691C(id)` opens the archive at `seg << 17 + off << 11`, reads
  entry 0 (the index) to 0x8019C0D0, and finds `id` there to get the
  entry number. It inflates that entry to 0x80043000, switches the open
  archive back to 0x300000, calls 0x80043000, and keeps the returned
  pointer at 0x802A532C. Every overlay id is in its bank's index. Some
  table ids (24, for example) are in no index and look stale.
- **bank0B's index** has a stale count: 9, but only 7 records follow (22
  bytes). `assets.py parse_index` must keep an explicit `count` when it
  differs from the record count. Today that bank falls back to `00.raw`.
- **ZeroJump**: the 0x130-byte zerojump stub is DMAd to 0x80042000 and
  TLB-mapped at virtual 0, so its splat VRAM should be 0x0. Callers do
  `jr $zero` with `li $t0, id` (high byte = module table, low byte =
  function). Tables are registered by `0x80001A30(n, table)` into
  0x8001BFC0[n]. Every module (main_code and each overlay) carries a full
  stub block of `00000008 2408xxxx` pairs, about 0x1640 bytes. Make it a
  `hasm` subsegment (`<module>_zerojmp`); the port replaces it with direct
  calls.
- **Overlay entry**: 0x80043000 is `return &main_func` (0x80043010).

## Text ends (checked against Bomberhackers/bm64 for us)

Text ends after the last `jr ra` or ZeroJump stub, rounded up to 16. It
ends before any RSP code, recognised as the first j/jal whose target is in
IMEM, `0x04001000..0x04002000`. That rule matches the reference for
boot_code (0x1AB80), main_code (0xB7A50; RSP code from there) and all 95
overlays. Eight overlays have no `.data`, only rodata, at that point.
eu: boot 0x1AB80 and main 0xB7A50 too.

## Plan in progress

- **One code image**, `assets/code.bin`, written at extract: ROM
  0..0x120000 as is, then every overlay inflated, back to back in bank and
  entry order. All overlay sizes are multiples of 16, 0x19F7D0 in total.
- **One splat config** over it (`bm64.<v>.yaml`, generated by layout.py):
  - code segments: boot_code (`[0x1000, hasm, entry]`, asm, data, bss
    0xC4A0 at 0x8001BFC0 from the entry), zerojump (vram 0, hasm),
    main_code (bss 0xE3D0 from the reference; verify), and `ovl_BB_EE` at
    0x80043000 (`exclusive_ram_id: overlay`, `symbol_name_format:
    BB_EE_$VRAM`, its own `dir`)
  - the rest are bins
  - overlay bss is unknown: derive it from references after the first split.
- **tools/rom.py** (new) builds the ROM: the code image's first 0x120000
  bytes, plus the banks from `assets.py build`, with overlay entries taken
  from the *rebuilt* code image (by the config's offsets), then the CRC
  and the sha1. It checks the two tables: every bank fits its size and
  every overlay id points to its bank.
- **Next after matching**: a SHIFT build. Symbolize the ROM references
  in code (zerojump's ROM range 0x1CBC0/0x1CCF0 in boot's entry, 0x40000
  and 0x30000 in boot, 0x30800 and the asset archive's 0x300000 in main;
  `lui 0x30`), then per-object data.
