# Text object boundaries that IDO's 16-byte padding can't show, because
# the function before them ends on a 16-byte boundary.  tools/layout.py
# splits the text at these as well as where the padding shows one
# (docs/LAYOUT.md, "Stage 2").  Each is us's image offset, the object's
# name; eu and jp get it through vermap.<version>.txt, unless the line
# gives that version's own start (its image offset), for an object that
# starts with other code there: the start us's maps to is then no
# boundary.  Add one only where the code shows the boundary.
#
#   <module> <us image offset> [<version>=<its image offset> ...]

# 4DE50 is the seven float compares, -O3; 4E030's wrappers call them with
# a jal, which -O3 would have inlined within one file.
main_code 4E030

# 47A80 (-O3) is five functions (func_8022D280 to func_8022DAB0, two of
# them called from 426E0) that call nothing in 48300 nor are called by it,
# and 48300 starts on the 16-byte boundary where they end.  Their data
# ends where 48300's begins, on 16-byte boundaries each: .data with a
# display list at 0x8029FCC8 whose end is followed by 8 zero bytes before
# 48300's function table at 0x8029FD40, .rodata (four words at
# 0x802A2D50) just before 48300's first float at 0x802A2D60, .bss up to
# 0x802A5558 before 48300's at 0x802A5560.
main_code 48300

# 9A5F0 (-O3): jp moved two functions to the end of the file (func_8028124C,
# func_80280DB4), so jp's object starts with them, at its own 0x9A340.
main_code 9A5F0 jp=9A340

# AD3D0 is the LZSS file decoder alone (called from 40FB0 and 87190);
# AD5B0, the EEPROM code, has none of its data: its .data starts on the
# 16-byte boundary after the decoder's one flag word (0x802A1DA0), and
# the decoder's ring buffer pointer and position are the last .bss before
# AFBF0's.
main_code AD5B0

# 97610 (-O2: nothing is inlined, as in its sibling 93850) is the
# tile-hazard code (its own list at 0x80090440, its own ZeroJump table
# 0x23 at 0x802A15AC); 96540, the controller-pak code before it, ends
# with func_8027CDA4 on a 16-byte boundary. Neither calls the other, and
# their .data (0x802A1570) and .bss (0x802B0180) start on 16-byte
# boundaries where the one ends and the other begins.
main_code 97610

# 78CA0 is a subtractive random number generator alone (Knuth's, as in
# Numerical Recipes' ran3: seed, refill, next int, next double); 78F60 is
# texture-drawing code.  Neither half calls the other, and the
# generator's data ends in its object's padding: its .rodata (1e-9, one
# double) is followed by 8 zero bytes before 78F60's floats at 0x802A3A20,
# and its .bss (index and table, 0xE8 bytes) by 8 bytes before
# 0x802AD0D0.
main_code 78F60

# 87D80 is three -O3 objects. IDO -O3 emits a file's functions callees
# first (roots in reverse source order, every call or address taken an
# edge), and the asm breaks that only across these two boundaries:
# 8027361C (87D80) takes the address of func_8027723C (8E730) and is
# emitted before it; 802752BC..802757E0 and 80275948 (8E730) call
# func_80277FC4 and func_80278D54 (926A0), 8027783C calls func_80278DBC.
# Split there, a draft's three files come out in the asm's order exactly.
# 8E730's .rodata starts on 16 at 0x802A3D20 (jtbl, after 87D80's last
# float at 0x802A3D1C); 926A0's .rodata after a zero pad word at
# 0x802A3DEC (0x802A3DF0), its .data at 0x802A14F0 and its .bss at
# 0x802AFE70, all 16-byte boundaries, and nothing before them uses those.
main_code 8E730
main_code 926A0

# A1EA0 (func_802876A0..func_80287FD4) is a second object after 9CAB0:
# 9CAB0's IPA statics (s-register parameters, func_802822E0..func_80286400)
# tie its callers from func_80282598 to func_802875B0 together, and none
# of 9CAB0 calls A1EA0 or the other way round. A1EA0's .data (-1, then a
# table of its four functions) starts on the 16-byte boundary 0x802A1B50
# where 9CAB0's tables end, and its .bss (0x802B0260, 0xB0 bytes) on the
# one where 9BFD0's ends; 9CAB0 has no .bss. As one file, its functions
# (emitted last, so first in the source) would have their data after
# 9CAB0's. func_80287680 ends 9CAB0 on a 16-byte boundary.
main_code A1EA0

# A8DE0 (-O3) is the 16 moving objects at 0x800BC770 (their task, their
# spawn table D_802A1D00 and their two function tables); A4CE0 before it
# is the 16 effects at 0x800BC528 and ends with the effect coroutine
# func_8028E540 on a 16-byte boundary.  A4CE0's .rodata ends at
# 0x802A4524 and is followed by 12 zero bytes before A8DE0's first float
# (20000.0f) at 0x802A4530, and A8DE0's .data starts with D_802A1D00, on
# the boundary after A4CE0's tables.  The emission order shows it too:
# each half has its globals first and its statics after, as one -O3
# object does.
main_code A8DE0

# 45170 (-O3) is the skeleton and animation code (model file chunks 2, 3
# and 7 read into a skeleton, its node tree, the animation tracks and
# their interpolation); 426E0 before it is the object pool, the draw
# loop and the per-object animation slots.  -O3 emits a file's callees
# before their callers, but 426E0's func_8022827C, func_80229D68,
# func_80229E38, func_80229F74 and func_8022A328 call func_8022C530,
# func_8022ABCC, func_8022BB88, func_8022C8B8, func_8022CF64,
# func_8022AF1C and func_8022D1D0, all emitted after them: a file
# boundary lies between func_8022A328 and func_8022ABCC.  The text
# there starts on 16 bytes only at func_8022A970 and func_8022AA50, with
# no padding before either; func_8022A970 frees what func_8022AF1C's
# chunk 3 allocated and only func_8022AA50 calls it.  The data agree:
# 426E0's .rodata (0.001f) ends in 12 zero bytes at 0x802A2D30, its
# .data (to D_8029F858's table) in 8 zero bytes at 0x8029F880, and its
# .bss at 0x802A54A0, each where 45170's references start.
main_code 45170

# 479D0 (-O3) is func_8022D1D0 alone, which builds a skeleton instance.
# It calls func_8022D15C (nine words copied from three .data vectors)
# and func_8022AEDC (two calls) with a jal, each once and outside any
# loop. IDO -O3 inlines a callee like that when it is in the same file,
# as a draft of 45170 with all of them in one file shows. The function
# before it, func_8022D15C, ends on a 16-byte boundary.
main_code 479D0
